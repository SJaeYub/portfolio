## 1. 업무 배경 및 목적 (Background & Purpose)

### 1.1 업무 개요

```
Alloy > Loki > Grafana로 이어지는 로그 기반 알람 파이프라인이 운영 중이나,
Alert 수신 메시지에 '서비스 에러 발생'이라는 문구만 표시되어 어떤 에러가 발생했는지
즉시 파악이 불가능한 상황이었음. 또한 Contact Point 템플릿에 오타가 존재하여
summary 필드가 빈칸으로 발송되는 문제도 확인됨.
이를 해결하기 위해 LogQL 쿼리 구조와 Contact Point 메시지 템플릿을 개선함.
```

### 1.2 업무 목적

- **해결하려는 문제**:
  - Contact Point 템플릿 오타(`.Annotaions`)로 인한 summary 빈칸 발송
  - 알람 메시지에 실제 에러 원인(어떤 클래스, 어떤 Exception)이 포함되지 않는 문제
- **성공 기준 (Definition of Done)**:
  - [ ] Contact Point 템플릿 오타 수정 완료
  - [ ] Alert 메시지에 에러 발생 클래스(logger)와 Exception 종류(exception_type) 포함
  - [ ] Loki High Cardinality 문제 없이 안전하게 동작
  - [ ] Alert 발송 지연 없음


### 2.3 조사 및 분석 내용

**Loki 라벨 아키텍처 이해 (핵심 전제 지식)**

Loki의 라벨은 생성 시점에 따라 두 종류로 구분된다:

| 구분 | 생성 시점 | 예시 | 특징 |
|------|----------|------|------|
| Ingestion Label (정적 라벨) | 수집 시점 (Alloy가 Loki로 전송 시) | app, container, namespace | Loki DB 인덱스에 물리적으로 저장. Stream 생성 기준 |
| Extracted Label (추출 라벨) | 쿼리 시점 (LogQL 실행 시) | logger, exception_type | RAM에서만 임시 처리 후 소멸. Stream 미생성 |

**Stream(스트림)이란?**

Loki는 라벨 조합별로 하나의 물리적 파일 폴더(Stream)를 생성한다.
정적 라벨이 유지되면 Stream 수도 유한하여 안정적으로 운영 가능하나,
동적 값(trace_id, guid 등)을 정적 라벨로 추가하면 Stream이 폭발적으로 증가하여
메모리 초과(OOM), 저장소 과부하, Loki 자체 차단(Log drop) 등 장애가 발생한다.

```
[정상 케이스] app="stock-service", env="prod" → Stream 1개
[장애 케이스] app="stock-service", trace_id="uuid-..." → 요청마다 새 Stream 생성 → OOM 위험
```

**쿼리 시점 임시 라벨의 부작용 범위 확인**

- Loki 측면: 임시 라벨은 Loki DB에 영구 저장되지 않고 쿼리 실행 중 RAM에서만 존재하다 소멸 → Stream 미생성 → 안전
- Grafana 측면: Alert Rule은 sum by(...)의 라벨 조합 1개당 Alert Instance 1개 생성 → 고유 값이 많은(동적) 라벨을 sum by에 포함하면 Alert Fanout(알람 폭탄) 발생 가능

#### Step 2. 로그 포맷 분석 및 pattern 파서 설계

**목적:** 정형화된 로그 포맷에서 logger, exception_type을 효율적으로 추출

**로그 포맷 구조 분석:**
```
표준 포맷: yyyy-MM-dd HH:mm:ss.SSS [LEVEL] PID --- [THREAD] Logger : Message

실제 예시:
2025-09-18 11:45:34.467 [ INFO] 1 --- [io-38080-exec-4] c.k.e.c.s.interceptor.KbankInterceptor : Interceptor request log guid:20250...
```

**pattern 파서 매핑 설계:**
```
`<time> [<level>] <pid> --- [<thread>] <logger> : <message>`
 ↑ 버림   ↑ 버림   ↑ 버림    ↑ 버림     ↑ 추출    ↑ 추출(1차)
```

**파서 선택 이유 (pattern vs regexp):**

| 파서 | 특징 | 선택 이유 |
|------|------|-----------|
| `\| pattern` | 정형화된 구조에 최적화, CPU 소비 최소 | 로그 포맷이 고정되어 있으므로 우선 적용 |
| `\| regexp` | 비정형 텍스트에서 특정 패턴 추출 | Exception 이름만 잘라내는 정밀 추출에 사용 |

#### Step 3. LogQL 쿼리 개선

**목적:** 에러 클래스(logger)와 Exception 종류(exception_type)를 쿼리 라벨로 추출

**변경 전 (Before):**
```logql
count_over_time(
  {app="stock-customer-service", container!~"istio.*"}
  |= "[ERROR]"
  [1m]
)
```
> 한계: 에러 횟수(숫자)만 반환. 로그 원문 텍스트는 완전히 버려짐

**변경 후 (After):**
```logql
sum by (app, logger, exception_type) (
  count_over_time(
    {app="stock-customer-service", container!~"istio.*"}  /* 1. 정적 라벨로 대상 스트림 선택 (고속 인덱스 검색) */
      |= "[ERROR]"                                         /* 2. [ERROR] 포함 로그만 1차 필터링 (문자열 검색, 정규식보다 빠름) */
      | pattern `<_> [<level>] <_> --- [<_>] <logger> : <_>`  /* 3. 로그 포맷에서 logger만 추출 (나머지는 <_>로 버림) */
      | regexp `(?P<exception_type>[a-zA-Z0-9_.]+Exception)`   /* 4. 로그 원문에서 *Exception으로 끝나는 단어만 추출 */
    [1m]                                                   /* 5. 직전 1분 범위만 조회 */
  )
)
/* sum by: 추출된 임시 라벨(logger, exception_type)과 정적 라벨(app)을 동등하게 그룹화 */
```

**쿼리 설계 원칙 (Filter First 최적화):**
```
1단계: {app="..."} → 정적 라벨로 대상 스트림 선택 (Loki 인덱스 활용, 최고속)
2단계: |= "[ERROR]" → 에러 로그만 필터링 (나머지 INFO/DEBUG 전부 제거)
3단계: | pattern → 남은 소수의 에러 로그에 대해서만 파싱 수행 (CPU 최소화)
4단계: | regexp → Exception 이름만 정밀 추출
```
> 1만 줄 중 2단계에서 에러 로그 수 줄로 축소 → pattern/regexp는 수 줄에만 적용됨 → 성능 이슈 없음

**full_error_msg를 sum by에서 제외한 이유:**

동적 에러 메시지 전체(guid, 트랜잭션 ID 포함)를 sum by에 포함하면:
```
{logger="KbankInterceptor", exception_type="NullPointerException", full_error_msg="... guid:a12b"} → Alert Instance 1
{logger="KbankInterceptor", exception_type="NullPointerException", full_error_msg="... guid:c89d"} → Alert Instance 2
...에러마다 별도 Alert Instance 생성 → Alert Fanout(알람 폭탄) 발생
```

따라서 `exception_type`(값 유한, 수십 가지)만 sum by에 포함하여 Alert Instance 수를 제어함.
상세 에러 메시지 확인이 필요한 경우 알람 수신 후 Grafana 대시보드에서 직접 로그를 조회.

```
Exception 종류(exception_type)를 쿼리 라벨로 추출하도록 개선.
Alert Rule Annotations summary에 동적 변수를 적용하여
알람 수신 시 실제 에러 원인을 즉시 파악 가능하도록 개선 완료.
Alloy 및 Loki 설정은 변경 없이 유지되어 High Cardinality 및 Stream 과부하 위험 없음.
```

## 7. 기술 메모 (Technical Notes)

### 7.1 핵심 기술 포인트

**Loki 라벨의 두 종류**
```
① Ingestion Label (수집 시 정적 라벨)
   - 생성: Alloy가 Loki로 전송 시 부착
   - 저장: Loki DB 인덱스에 물리적으로 영구 저장
   - 역할: Stream 생성 기준
   - 예: app, container, namespace
   - 주의: 동적 값(guid, trace_id 등)을 정적 라벨로 추가하면 Stream 폭발(High Cardinality) 장애 발생

② Extracted Label (쿼리 시 임시 라벨)
   - 생성: LogQL 실행 시 | pattern, | regexp 파서가 로그 텍스트에서 실시간 추출
   - 저장: Loki DB에 저장되지 않음. RAM에서만 처리 후 소멸 → Stream 미생성
   - 역할: 쿼리 결과의 그룹화(sum by), Grafana Alert 라벨 전달
   - 예: logger, exception_type, error_msg
```

**Grafana Alert Fanout (알람 폭탄) 주의**
```
Alert Rule은 sum by(...)의 고유 라벨 조합 1개당 Alert Instance 1개 생성.
동적 값(guid 등)을 sum by에 포함하면 동일 에러가 수백 개의 Alert Instance로 분리됨 → 알람 폭탄.
→ sum by에는 값의 종류가 유한한(수십~수백 가지) 라벨만 포함할 것.
```

**Filter First 최적화 패턴**
```
{정적 라벨 필터}    → 인덱스 검색으로 대상 스트림만 선택 (최고속)
|= "키워드"        → 문자열 매칭으로 대다수 로그 제거 (정규식보다 빠름)
| pattern `...`    → 남은 소수 로그에만 구조 파싱 적용
| regexp `...`     → 정밀 추출 (CPU 부하 최소화)

→ 1만 줄 → 수 줄로 압축 후 파싱 수행 = 사실상 CPU 부하 없음
```

**쿼리 시점 임시 라벨의 알람 발송 지연 없음 이유**
```
① 조회 범위 [1m]: 조회 대상 데이터 자체가 극소량
② Filter First 패턴: 파싱 대상을 에러 로그 수 줄로 사전 축소
③ Loki 분산 처리: 짧은 범위 쿼리는 병렬 처리로 ms 단위 완료
```

**Loki 스트림 개념**
```
Stream = 라벨 조합으로 결정되는 물리적 로그 파일 폴더(그릇).
라벨 조합이 많을수록 그릇 수가 늘어남.
Loki 철학: "라벨은 최소한으로, 파싱은 쿼리 시점에"
→ 정적 라벨은 최소한으로 유지하고, 에러 내용 추출은 LogQL 파서(| pattern, | regexp)로 처리.
```

### 7.3 알게 된 점 / 개선 아이디어

- Loki에서 sum by의 라벨들은 Loki에 사전 등록이 필요 없으며, 쿼리 파이프라인에서 실시간으로 생성되는 임시 라벨임을 명확히 이해
- Exception 키워드가 없는 에러 케이스(예: OOM, 커스텀 에러 코드 등)에 대한 추가 모니터링 필요
- 상세 에러 메시지가 필요한 경우 알람 → Grafana 대시보드 링크를 통한 드릴다운 방식 구성이 올바른 설계 방향
