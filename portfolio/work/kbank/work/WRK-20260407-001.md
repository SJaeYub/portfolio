## 1. 업무 배경 및 목적 (Background & Purpose)

### 1.1 업무 개요

```
기존 Alloy → Loki 로그 수집 파이프라인이 운영 중인 상태에서,
TransactionLog 타입의 로그를 Loki뿐 아니라 AWS MSK(Kafka)로도 동시에 전송해야 하는 요구사항 발생.

이전 작업(WRK-20260320-001)에서 log_type 라벨이 이미 추출되어 있는 상태를 활용하여,
기존 파이프라인은 유지하면서 TransactionLog만 MSK로 분기(fan-out)하는 구조로 확장함.
Alloy는 Helm으로 구성되어 있으며 config-alloy.json 파일을 values.yaml에서 참조하는 방식으로 운영 중.
```

### 1.2 업무 목적

- **해결하려는 문제**: TransactionLog 타입 로그를 Kafka 소비자(MSK)가 실시간으로 수신할 수 있도록 Alloy 파이프라인 확장
- **성공 기준 (Definition of Done)**:
  - [ ] 기존 Loki 전송 파이프라인 영향 없이 TransactionLog 분기 동작
  - [ ] MSK로 TransactionLog만 정상 전송 확인
  - [ ] MSK 장애 시 Loki 전송 경로 보호 (memory_limiter 적용)
  - [ ] Alloy v1.1.1 API 문법 준수 확인

### 1.3 관련 배경 지식 / 시스템 설명

**현재 파이프라인 구조 (AS-IS)**
```
[K8s Pods 로그]
  └─► loki.source.file "kubernetes_pods"
        └─► loki.process "kubernetes_pods"
              │  (stage.cri → multiline → regex → labels → drop)
              │  log_type 라벨 이미 추출 완료 (WRK-20260320-001)
              └─► loki.write.default  →  Loki
```

**Alloy 컴포넌트 생태계 구분**

Alloy 내부에는 두 가지 완전히 분리된 파이프라인 계열이 존재하며, 서로 다른 Go 내부 타입을 사용한다:

| 계열 | 내부 타입 | 주요 컴포넌트 |
|------|----------|--------------|
| `loki.*` | `loki.Entry` (Loki 고유 Go 구조체) | `loki.source.*`, `loki.process`, `loki.write` |
| `otelcol.*` | `pdata.Logs` (OpenTelemetry Go 구조체) | `otelcol.receiver.*`, `otelcol.processor.*`, `otelcol.exporter.*` |

두 계열은 Go 타입 수준에서 완전히 달라 직접 연결 불가. 브리지 컴포넌트(`otelcol.receiver.loki`)가 필요한 이유다.

**Kafka 전송 컴포넌트 현황 (Alloy v1.1.1 기준)**

| 컴포넌트 | 방향 | 비고 |
|---------|------|------|
| `otelcol.exporter.kafka` | → Kafka 쓰기 | 유일한 Kafka 전송 컴포넌트 |
| `otelcol.receiver.kafka` | Kafka 읽기 → | - |
| `loki.source.kafka` | Kafka 읽기 → Loki | 읽기 전용 |
| `loki.exporter.kafka` | - | **존재하지 않음** |

→ loki 파이프라인에서 Kafka로 가는 직접 경로가 없으므로, `otelcol.receiver.loki` 브리지를 반드시 경유해야 한다.

## 2. 현황 분석 (Current State Analysis)

### 2.1 현재 구조 / AS-IS

```hcl
// config-alloy.json 기존 핵심 구조

loki.process "kubernetes_pods" {
  stage.cri {}

  stage.multiline {
    firstline     = "^\\d{4}-\\d{2}-\\d{2} \\d{2}:\\d{2}:\\d{2}.\\d{3}"
    max_wait_time = "3s"
    max_lines     = 128
  }

  // log_type 라벨 이미 추출 중 (WRK-20260320-001에서 적용)
  stage.regex {
    expression = "\\[\\s?(?P<level>INFO|WARN|DEBUG|ERROR|FATAL|TRACE)\\]\\s+\\[(?P<log_type>TransactionLog|AccessLog|ApplicationLog)\\]"
  }

  stage.regex {
    expression = "[\"']?status[\"']?\\s*[:=]\\s*(?P<status>\\d+)"
  }

  stage.labels {
    values = { "log_level" = "level", "status" = "status", "log_type" = "log_type" }
  }

  stage.drop {
    older_than = "60m"
  }

  // ⚠️ 현재: Loki에만 전송
  forward_to = [loki.write.default.receiver]
}
```

### 2.2 문제점 / 개선 필요 사항

| # | 문제점 | 영향 | 우선순위 |
|---|--------|------|----------|
| 1 | TransactionLog가 Loki에만 수집되며, MSK 소비자가 실시간 접근 불가 | 트랜잭션 로그 기반 이벤트 처리 파이프라인 구축 불가 | 높음 |

### 2.3 핵심 설계 검토 사항

**① fan-out을 loki.source.file에서 바로 분기하면 안 되는 이유**

`transaction_msk_filter`의 필터 조건(`{log_type!="TransactionLog"}`)은 `stage.labels`에서 부착된 `log_type` 라벨에 의존한다. `loki.source.file`에서 나온 원본 로그에는 이 라벨이 없으므로, `kubernetes_pods` 프로세스를 거치기 전에 분기하면 모든 로그가 드롭된다.

```
[원본 로그 상태] - loki.source.file 출력
  라벨: {filename="/var/log/app.log"}  ← log_type 없음

[kubernetes_pods 처리 후 상태]
  라벨: {log_level="INFO", log_type="TransactionLog", status="200"}  ← log_type 존재
```

따라서 `kubernetes_pods` 이후 꼬리물기(fan-out) 구조가 필수.

**② fan-out의 blocking 특성 (중요 위험 요소)**

Alloy의 `forward_to = [A, B]`는 병렬이 아닌 **순차(blocking)** 방식으로 동작한다 (GitHub issue #2194 공식 확인).

```
로그 1건 도착
  ├─► A (loki.write.default) 완료 대기
  └─► B (transaction_msk_filter) 완료 대기  ← B가 느려지면 A도 지연
```

MSK 장애 시 back-pressure가 발생하면 아래 연쇄 차단이 발생할 수 있다:

```
MSK 장애
  └─► otelcol.exporter.kafka backpressure
        └─► otelcol.processor.batch 큐 가득 참
              └─► otelcol.receiver.loki 블록
                    └─► loki.process.transaction_msk_filter 블록
                          └─► forward_to 전체 블록  ← ⚠️ Loki 전송도 중단
```

→ **대응**: `otelcol.processor.memory_limiter`를 batch 앞에 삽입하여 메모리 한계 초과 시 드롭, Loki 경로 보호.

**③ memory_limiter는 반드시 batch 앞에 위치해야 하는 이유**

공식 문서 권장 순서: `memory_limiter → batch → kafka exporter`

batch가 먼저 오면 이미 배치로 묶인 대량 데이터가 메모리를 초과한 뒤에야 감지되어 제어가 늦어진다.

**④ otelcol.receiver.loki의 실체**

"OTel 변환"은 데이터 포맷 변환이 아닌 **Go 내부 구조체 타입 교체**다. 로그 내용은 그대로 유지된다.

```
loki.Entry                           pdata.Logs
{                           ──►      {
  Line: "2026-04-07 [INFO]..."          Body: "2026-04-07 [INFO]..."
  Labels: {log_type: "Tx..."}           Attributes: {log_type: "Tx..."}
  Timestamp: 2026-04-07T...             Timestamp: 2026-04-07T...
}                                     }
     otelcol.receiver.loki "kafka_bridge"
     역할: Go 구조체 타입 변환만 수행 (데이터 손실 없음)
```

Kafka 토픽에 실제로 도착하는 형식은 `encoding` 설정이 결정하며, MSK는 Alloy 내부 타입 변환과 무관하게 최종 바이트만 수신한다.

| encoding | Kafka 토픽 도착 형식 |
|----------|-------------------|
| `otlp_json` | `{"resourceLogs":[{"resource":{"attributes":[{"key":"log_type",...}]},"scopeLogs":[...]}]}` |
| `otlp_proto` | 바이너리 protobuf |
| `raw` | `"2026-04-07 [INFO] [TransactionLog] 결제 완료"` (라벨 메타데이터 제거) |

**⑤ Alloy v1.1.1 API 주의사항**

`otelcol.exporter.kafka`의 `topic`과 `encoding`은 v1.9.x부터 `logs {}` 블록 안으로 이동했다. v1.1.1에서 `logs {}` 블록을 사용하면 컴포넌트가 정상 기동되지 않으므로, **최상위 인자**로 선언해야 한다.

```hcl
// ❌ v1.9.x+ 문법 (v1.1.1에서 기동 실패)
otelcol.exporter.kafka "msk" {
  logs {
    topic    = "transaction-logs"
    encoding = "otlp_json"
  }
}

// ✅ v1.1.1 문법 (최상위 인자)
otelcol.exporter.kafka "msk" {
  topic    = "transaction-logs"
  encoding = "otlp_json"
  ...
}
```

#### Step 2. 신규 컴포넌트 5개 추가

**목적:** TransactionLog를 MSK로 안전하게 전송하는 보조 파이프라인 구성

```hcl
// ============================================================
// [신규 1] TransactionLog만 통과시키는 필터
//   - log_type 라벨은 kubernetes_pods에서 이미 부착됨
//   - selector는 Loki 스트림 라벨 기반 LogQL 문법
// ============================================================
loki.process "transaction_msk_filter" {

  stage.match {
    // log_type이 TransactionLog가 아닌 모든 로그 드롭
    selector            = `{log_type!="TransactionLog"}`
    action              = "drop"
    drop_counter_reason = "not_transaction_log"
  }

  // 공식 loki → otelcol 브리지로 전달
  forward_to = [otelcol.receiver.loki.kafka_bridge.receiver]
}

// ============================================================
// [신규 2] loki 파이프라인 → otelcol 파이프라인 공식 브리지
//   - loki.Entry(Go 구조체) → pdata.Logs(Go 구조체) 타입 변환
//   - 로그 내용, 라벨, 타임스탬프 등 모든 데이터 보존
//   - 이 변환은 Alloy 내부 배관 처리이며, Kafka 토픽에는 encoding 설정이 결정
// ============================================================
otelcol.receiver.loki "kafka_bridge" {
  output {
    logs = [otelcol.processor.memory_limiter.kafka_mem_limit.input]
  }
}

// ============================================================
// [신규 3] 메모리 보호막 (공식 권장: batch 앞에 위치)
//   - MSK 장애 → back-pressure → 메모리 초과 시 이 지점에서 드롭
//   - batch 앞에 있어야 대량 배치 적재 전에 선제 차단 가능
//   - limit은 Alloy Pod 메모리 limit의 50% 수준으로 설정 권장
// ============================================================
otelcol.processor.memory_limiter "kafka_mem_limit" {
  check_interval = "1s"
  limit          = "200MiB"   // Pod memory limit 기준으로 조정 필요
  spike_limit    = "40MiB"

  output {
    logs = [otelcol.processor.batch.kafka_batch.input]
  }
}

// ============================================================
// [신규 4] 배치 프로세서
//   - 기본값: timeout 200ms / send_batch_size 8192건 중 먼저 도달 시 발송
//   - 로그 1건씩 전송 시 TCP 오버헤드 방지, Kafka 브로커 부하 감소
//   - 200ms = near-realtime 수준 (로그 파이프라인 허용 지연 수초 대비 충분)
// ============================================================
otelcol.processor.batch "kafka_batch" {
  timeout         = "200ms"
  send_batch_size = 2000

  output {
    logs = [otelcol.exporter.kafka.msk.input]
  }
}

// ============================================================
// [신규 5] MSK Kafka Exporter (Alloy v1.1.1 문법 기준)
//   - v1.1.1: topic/encoding은 최상위 인자 (logs {} 블록 아님)
//   - 포트 9092: 완전 평문(PLAINTEXT) → authentication 블록 불필요
//   - brokers: Bootstrap Broker 3개 전체 명시 (가용성 확보)
//   - protocol_version 2.0.0: MSK Kafka 2.x~3.x 전 버전 호환 안전 최소 버전
// ============================================================
otelcol.exporter.kafka "msk" {
  brokers = [
    "b-1.your-cluster.xxxx.kafka.ap-northeast-2.amazonaws.com:9092",
    "b-2.your-cluster.xxxx.kafka.ap-northeast-2.amazonaws.com:9092",
    "b-3.your-cluster.xxxx.kafka.ap-northeast-2.amazonaws.com:9092",
  ]
  protocol_version = "2.0.0"

  // v1.1.1: 최상위 인자로 선언
  topic    = "transaction-logs"
  encoding = "otlp_json"   // raw: 순수 로그 문자열만 전송 / otlp_json: 라벨 메타데이터 포함

  // 포트 9092 = 완전 평문: authentication 블록 전체 제거

  producer {
    compression = "snappy"   // 전송 효율화 (lz4도 선택 가능)
  }
}
```

## 7. 기술 메모 (Technical Notes)

### 7.1 핵심 기술 포인트

**Alloy fan-out (forward_to 복수 지정) 동작 원리**
```
forward_to = [A, B]는 병렬이 아닌 순차(blocking) 처리.
A 완료 → B 전달 순으로 동작하므로, B(느린 경로)가 막히면 A도 지연.
→ 빠른 경로(Loki)를 앞에 배치하고, memory_limiter로 느린 경로(MSK) 차단 시 드롭 처리.
```

**otelcol.receiver.loki — 브리지의 실체**
```
역할: loki.Entry(Loki Go 구조체) → pdata.Logs(OTel Go 구조체) 타입 변환
실체: 데이터 포맷 변환이 아닌 내부 배관 연결 어댑터
결과: 로그 내용, 라벨, 타임스탬프 모두 보존
MSK 영향: 없음. encoding 설정이 Kafka 도착 형식을 별도로 결정
```

**memory_limiter 위치 원칙 (공식 권장)**
```
memory_limiter → batch → exporter  ← ✅ 공식 권장 순서
batch → memory_limiter → exporter  ← ❌ batch가 메모리 쌓은 뒤 감지되어 늦음
```

**MSK 포트별 인증 방식**

| 포트 | 인증 | TLS | Alloy 설정 |
|------|------|-----|-----------|
| 9092 | 없음 (PLAINTEXT) | 없음 | `authentication` 블록 전체 제거 |
| 9096 | SASL/SCRAM | 있음 | `mechanism = "SCRAM-SHA-512"` |
| 9098 | IAM (OAUTHBEARER) | 필수 | `mechanism = "AWS_MSK_IAM_OAUTHBEARER"` + IRSA |

**brokers 배열에 전체 명시하는 이유**
```
brokers는 Bootstrap Broker 목록.
클라이언트는 이 중 하나에 연결하여 전체 클러스터 토폴로지(파티션 리더 위치 등)를 받음.
이론상 1개만 살아있어도 동작하나, 3개 전체 명시 시 Bootstrap 연결 자체의 단일 장애점 제거.
```

**Alloy v1.1.1 vs v1.9.x+ API 차이**
```hcl
// v1.1.1: topic/encoding 최상위 인자
otelcol.exporter.kafka "msk" {
  topic    = "transaction-logs"
  encoding = "otlp_json"
}

// v1.9.x+: logs {} 블록 내부로 이동
otelcol.exporter.kafka "msk" {
  logs {
    topic    = "transaction-logs"
    encoding = "otlp_json"
  }
}
```

**otelcol.processor.batch 기본값**
```
timeout         = "200ms"    // 시간 기준 발송 (0.2초, near-realtime)
send_batch_size = 8192       // 건수 기준 발송 (먼저 도달하는 조건 적용)
→ 실시간성 강화 필요 시 timeout = "50ms"로 단축 가능 (단, Kafka 브로커 요청 빈도 증가)
```

### 7.3 알게 된 점 / 개선 아이디어

- Alloy의 loki 파이프라인과 otelcol 파이프라인은 Go 타입 수준에서 완전히 분리되어 있으며, 현재 버전 기준 Kafka 전송은 otelcol 계열만 지원하므로 브리지 컴포넌트가 구조적 필수 조건임
- fan-out의 blocking 특성은 설계 시 반드시 고려해야 하며, 느린 외부 시스템으로의 분기는 memory_limiter로 보호하는 것이 공식 권장 패턴
- `encoding = "raw"` 사용 시 Alloy가 부착한 라벨 메타데이터가 Kafka 도착 메시지에서 제거되므로, MSK 컨슈머 요구사항에 따라 encoding 선택이 중요
- Alloy 버전 업그레이드 시 otelcol.exporter.kafka의 API 변경 여부를 CHANGELOG에서 반드시 확인 필요
