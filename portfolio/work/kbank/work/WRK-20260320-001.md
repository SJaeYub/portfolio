## 1. 업무 배경 및 목적 (Background & Purpose)

### 1.1 업무 개요

```
기존 Alloy → Loki 로그 수집 파이프라인에서는 [LEVEL]과 status만 라벨로 부착하고 있었음.
로그 포맷에 [LOGTYPE] 필드(TransactionLog / AccessLog / ApplicationLog)가 추가됨에 따라
Loki에서 로그 타입별 필터링 및 분석이 가능하도록 log_type 라벨을 신규 추가하는 작업 수행.
```

### 1.2 업무 목적

- **해결하려는 문제**: 로그 포맷에 추가된 [LOGTYPE] 필드를 Loki 라벨로 수집하지 않아 로그 타입별 조회 및 알람 설정이 불가한 상태
- **성공 기준 (Definition of Done)**:
  - [ ] config-alloy.json의 `stage.regex` 정규식에 `log_type` 캡처 그룹 추가
  - [ ] `stage.labels`에 `log_type` 라벨 등록
  - [ ] Loki에서 `log_type` 라벨로 로그 필터링 정상 동작 확인
  - [ ] 기존 `log_level`, `status` 라벨 정상 동작 유지 확인

### 1.3 관련 배경 지식 / 시스템 설명

```
[파이프라인 구조]
애플리케이션 파드 → Alloy (로그 수집 및 라벨 부착) → Loki (저장) → Grafana (조회/알람)

[로그 포맷]
변경 전: yyyy-MM-dd HH:mm:ss.SSS [LEVEL] PID --- [THREAD] Logger:Message
변경 후: yyyy-MM-dd HH:mm:ss.SSS [LEVEL] [LOGTYPE] PID --- [THREAD] Logger:Message

실제 예시:
2024-01-15 10:30:45.123 [INFO] [TransactionLog] 12345 --- [main] com.example.Service:Message

[LOGTYPE] 값 3종:
- TransactionLog: 트랜잭션 로그
- AccessLog: 접근 로그
- ApplicationLog: 애플리케이션 일반 로그

[Alloy 라벨 부착 원리]
- stage.regex: 정규식으로 로그 텍스트에서 캡처 그룹(named group)을 추출 → 임시 변수 생성
- stage.labels: stage.regex에서 추출된 임시 변수를 Loki 라벨로 등록
- 등록된 라벨은 Loki에 Stream 생성 기준이 되므로, 값의 종류가 유한한 필드만 라벨로 등록해야 함
  (log_type: 3종류 → 안전)
```

## 2. 현황 분석 (Current State Analysis)

### 2.1 현재 구조 / AS-IS

```
[기존 config-alloy.json loki.process 블록 구조]

loki.process "kubernetes_pods" {
  stage.cri {}

  stage.multiline {
    firstline     = "^\\d{4}-\\d{2}-\\d{2} \\d{2}:\\d{2}:\\d{2}\\.\\d{3}"
    max_wait_time = "3s"
    max_lines     = 128
  }

  // ① level 추출
  stage.regex {
    expression = "\\[\\s?(?P<level>INFO|WARN|DEBUG|ERROR|FATAL|TRACE)\\]"

  // ② status 코드 추출 (HTTP 상태코드, JSON/파라미터 형태)
  stage.regex {
    expression = "[\"']?status[\"']?\\s*[:=]\\s*(?P<status>\\d+)"
  }

  // 라벨 등록
  stage.labels {
    values = {"log_level" = "level", "status" = "status",}
  }

  stage.drop {
    older_than = "60m"
  }

  forward_to = [loki.write.default.receiver]
}
```

### 2.2 문제점 / 개선 필요 사항

| # | 문제점 | 영향 | 우선순위 |
|---|--------|------|----------|
| 1 | 로그 포맷에 추가된 [LOGTYPE] 필드가 Loki 라벨로 수집되지 않음 | 로그 타입별 Loki 쿼리 필터링 불가, 로그 타입별 알람 설정 불가 | 높음 |

### 2.3 조사 및 분석 내용

**라벨 통합 vs 분리 여부 검토**

| 구분 | 통합 (level + log_type 동일 regex) | 분리 (별도 regex 블록) |
|------|-------------------------------------|------------------------|
| **성능** | 로그 1줄당 regex 실행 2회 → 1회로 감소 | regex 실행 횟수 유지 |
| **원자성** | level과 log_type을 동일 컨텍스트에서 추출, 한쪽만 매칭되는 오류 없음 | 한쪽 매칭 실패 시 나머지만 부착될 수 있음 |
| **유지보수** | 관련 필드를 한 블록에서 관리 | 블록 분산으로 관리 복잡도 증가 |
| **적합 조건** | 두 필드가 항상 같은 위치에 함께 등장 | 한쪽 필드가 선택적으로 존재 |

**결론**: 현재 로그 포맷에서 `[LEVEL]`과 `[LOGTYPE]`은 항상 고정 위치에 함께 등장하므로 **통합** 방식이 적합.
`status` 코드는 HTTP 응답 JSON/파라미터 내부에서 별도 패턴으로 파싱하는 용도로, 포맷이 전혀 다르므로 **분리 유지**.

```
[LEVEL] [LOGTYPE] — 고정 위치, 항상 쌍으로 등장 → 통합
status             — JSON/파라미터에서 별도 파싱   → 분리 유지
```

#### Step 1. stage.regex ① 정규식 확장

**목적:** 기존 level 단독 추출 regex에 log_type 캡처 그룹을 추가하여 두 필드를 한 번에 추출

**변경 전 (Before):**
```hcl
stage.regex {
  expression = "\\[\\s?(?P<level>INFO|WARN|DEBUG|ERROR|FATAL|TRACE)\\]"

```

**변경 후 (After):**
```hcl
stage.regex {
  expression = "\\[\\s?(?P<level>INFO|WARN|DEBUG|ERROR|FATAL|TRACE)\\]\\s+\\[(?P<log_type>TransactionLog|AccessLog|ApplicationLog)\\]"
}
```

**정규식 구조 분해:**

| 패턴 | 역할 |
|------|------|
| `\\[\\s?` | `[` 문자 매칭 (앞 공백 허용) |
| `(?P<level>INFO\|WARN\|DEBUG\|ERROR\|FATAL\|TRACE)` | LEVEL 캡처 그룹 — level 임시 변수로 저장 |
| `\\]\\s+` | `]` 이후 공백(1개 이상) 매칭 |
| `\\[` | `[` 문자 매칭 |
| `(?P<log_type>TransactionLog\|AccessLog\|ApplicationLog)` | LOGTYPE 캡처 그룹 — log_type 임시 변수로 저장 |
| `\\]` | `]` 문자 매칭 |

**적용 예시:**
```
입력: "2024-01-15 10:30:45.123 [INFO] [TransactionLog] 12345 --- [main] com.example.Service:Message"

추출 결과:
  level    = "INFO"
  log_type = "TransactionLog"
```

## 7. 기술 메모 (Technical Notes)

### 7.1 핵심 기술 포인트

**Alloy stage.regex 동작 원리**
```
stage.regex는 로그 텍스트 전체를 대상으로 정규식을 실행하여
Named Capture Group((?P<이름>패턴))으로 지정된 값을 임시 변수로 추출한다.
추출된 임시 변수는 stage.labels에서 Loki 라벨로 등록하거나,
stage.template 등 다른 stage에서 참조할 수 있다.
```

**stage.regex 통합 vs 분리 판단 기준**
```
필드가 항상 같은 위치에 함께 등장 → 통합 (성능, 원자성, 유지보수 우위)
필드가 선택적으로 존재하거나 위치가 다름 → 분리 (안전성 우위)

현재 케이스:
  [LEVEL] [LOGTYPE] — 항상 고정 위치에 쌍으로 등장 → 통합 ✅
  status             — JSON/파라미터에서 별도 파싱   → 분리 유지 ✅
```

**Loki 라벨 카디널리티 관점**
```
log_type 값: TransactionLog, AccessLog, ApplicationLog (3종 고정)
→ Stream 증가 최대 3배 (기존 Stream 수 × 3)
→ 값이 유한하고 종류가 적어 High Cardinality 위험 없음 ✅

주의: 동적 값(guid, 사용자 ID 등)을 라벨로 추가하면 Stream 폭발 위험
```

**stage.labels null 값 축약 문법**
```hcl
// 아래 두 표현은 동일하게 동작
"log_type" = "log_type"   // 명시적 표현: 우측은 stage.regex의 캡처 그룹 이름
"log_type" = null          // 축약 표현: Alloy가 동일 이름의 캡처 그룹을 자동 참조
```

### 7.3 알게 된 점 / 개선 아이디어

- Alloy의 `stage.regex`는 같은 블록에서 여러 Named Capture Group을 동시에 추출할 수 있으므로, 같은 위치에 등장하는 필드는 통합하는 것이 성능상 유리함
- LOGTYPE 필드가 추후 3종 이상으로 확장될 경우 정규식의 alternation(`|`) 목록을 업데이트해야 하므로, 가능하면 `[A-Za-z]+` 같은 유연한 패턴으로 확장성을 고려하는 것도 방법
- log_type 라벨이 확보되면 Grafana Alert Rule에서 `{log_type="TransactionLog", log_level="ERROR"}`와 같은 복합 조건 알람 구성이 가능해짐
