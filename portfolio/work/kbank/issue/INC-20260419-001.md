## 1. 현상 (Symptom)

### 1.1 장애 개요

```
AWS NLB(IP 타겟 모드)에 연결된 istio-gateway 네임스페이스의 internal-gateway 파드 타겟이
모두 Unhealthy 상태로 전환되면서 NLB로부터의 인바운드 트래픽이 완전히 단절되었다.
istio-gateway 파드 및 aws-load-balancer-controller 파드는 모두 Running 정상 상태였으며,
애플리케이션 레벨 문제가 아닌 NLB 헬스 체크 실패로 인한 트래픽 차단이었다.
```

### 1.2 현상 상세

- **영향받은 서비스/시스템**: istio-gateway 네임스페이스 / internal-gateway Service (NLB IP 타겟 모드)
- **오류 메시지 / 증상**:
  ```
  # AWS 콘솔: Target Group 전체 타겟 Unhealthy
  # aws-load-balancer-controller 파드 로그:
  expect exactly one securitygroup tagged with kubernetes.io/cluster/<클러스터명>
  for eni eni-***, got: []
  ```
- **정상 동작 기준**: NLB Target Group 내 internal-gateway 파드 IP가 Healthy 상태로 등록되어 인바운드 트래픽 정상 수신
- **비정상 동작 내용**: Target Group 전체 Unhealthy → NLB가 트래픽을 파드로 전달하지 않아 인바운드 서비스 완전 단절

### 1.3 영향도

- **서비스 중단 여부**: 완전 중단 (NLB로부터의 트래픽 전체 단절)
- **영향 사용자 수**: -
- **비즈니스 영향**: internal-gateway를 통해 인입되는 전체 서비스 트래픽 단절

## 3. 원인 분석 (Root Cause Analysis) — 5 Whys

### 3.1 직접 원인 (What happened?)

```
노드그룹에 신규 보안 그룹(SG)을 추가하면서 노드 ENI에 SG가 2개가 되었다.
두 SG 모두 kubernetes.io/cluster/<클러스터명> 태그가 없는 상태였기 때문에
aws-load-balancer-controller가 NLB → 파드 구간의 인바운드 규칙을 적용할
대상 SG를 특정하지 못해 Reconcile 실패 → NLB 헬스 체크 차단 → 전체 Unhealthy
```

### 3.2 5 Whys 분석

| 단계 | 질문 | 답변 | 근거/증거 |
|------|------|------|-----------|
| **Why 1** | 왜 NLB 타겟이 Unhealthy가 됐는가? | aws-lb-controller가 노드 SG에 `NLB → 파드 포트` 인바운드 규칙을 추가하지 못해 NLB 헬스 체크 패킷이 SG 레벨에서 차단됨 | aws-lb-controller 로그: `expect exactly one securitygroup tagged with kubernetes.io/cluster/...` |
| **Why 2** | 왜 컨트롤러가 SG에 규칙을 추가하지 못했는가? | 관리 대상 SG를 특정하지 못했음. 컨트롤러는 `kubernetes.io/cluster/<name>` 태그가 달린 SG가 정확히 1개여야 동작하는데 해당 태그가 달린 SG가 0개였음 | 노드 ENI에 부착된 SG 목록 확인 → 2개 모두 태그 없음 |
| **Why 3** | 왜 태그가 달린 SG가 0개였는가? | 기존 SG 1개만 있을 때는 태그 없이도 컨트롤러가 유일한 SG를 묵시적으로 사용했기 때문에 태그 부재가 문제로 드러나지 않았음. 신규 SG 추가 후 2개가 되면서 태그 기반 식별이 필요해졌으나 둘 다 태그가 없었음 | SG 1개일 때의 정상 동작 이력 확인 |
| **Why 4** | 왜 신규 SG 추가 시 태그를 부여하지 않았는가? | aws-lb-controller가 `kubernetes.io/cluster` 태그로 관리 대상 SG를 식별한다는 메커니즘을 인지하지 못한 상태에서 작업이 수행됨 | 변경 작업 기록 검토 |
| **Why 5** | 왜 해당 메커니즘을 인지하지 못했는가? | 노드그룹 SG 변경 작업에 대한 사전 검토 프로세스 및 aws-lb-controller 동작 원리 관련 내부 가이드가 부재했음 | 관련 런북/체크리스트 미존재 확인 |

### 3.3 근본 원인 (Root Cause)

```
aws-load-balancer-controller는 노드 ENI에 부착된 SG 중
kubernetes.io/cluster/<클러스터명> 태그가 달린 SG를 정확히 1개 요구하는 설계이나,
이 메커니즘에 대한 팀 내 인지 부재 및 SG 변경 작업 시 사전 확인 프로세스가 없어
신규 SG 추가 후 태그 미설정 상태가 서비스 장애로 이어졌다.
```

### 3.4 기여 요인 (Contributing Factors)

- **SG 1개일 때의 묵시적 동작**: SG가 1개뿐일 때는 태그 없이도 정상 동작하므로 태그 필요성이 평소에 드러나지 않았음
- **NLB SG 부재 구조**: NLB에 SG가 없어 트래픽 제어가 전적으로 노드 SG에 의존하는 구조이므로, SG 규칙 주입 실패 시 즉시 전체 트래픽 단절로 이어짐
- **알람 부재**: aws-lb-controller 에러 로그 및 NLB Target Unhealthy 상태에 대한 모니터링 알람이 없어 탐지가 지연됨

### 4.2 임시 조치 (Workaround)

```
해당 없음.
태그 추가 즉시 aws-lb-controller Reconcile이 트리거되어 규칙이 복원되고 Healthy로 전환됨.
별도의 임시 조치 없이 근본 조치로 바로 복구됨.
```

### 4.3 근본 조치 (Permanent Fix)

```
기존 노드그룹 보안 그룹(sg-기존)에 아래 태그 추가:
  Key:   kubernetes.io/cluster/<클러스터명>
  Value: owned

조치 결과:
  - aws-lb-controller가 해당 SG를 관리 대상으로 식별
  - Reconcile 수행: sg-기존에 "NLB 서브넷 CIDR → istio-gateway 파드 포트" 인바운드 규칙 자동 추가
  - NLB Target Group 전체 Healthy 전환, 트래픽 복구
  - sg-신규는 태그 없이 그대로 유지 (노드그룹에는 정상 적용, 컨트롤러 관리 범위 외)
```

```bash
# 조치에 사용한 명령어
aws ec2 create-tags \
  --resources <sg-기존-ID> \
  --tags Key=kubernetes.io/cluster/<CLUSTER_NAME>,Value=owned

# 복구 확인: 태그가 달린 SG 목록 조회
aws ec2 describe-security-groups \
  --filters "Name=tag-key,Values=kubernetes.io/cluster/<CLUSTER_NAME>" \
  --query 'SecurityGroups[*].{ID:GroupId,Name:GroupName}' \
  --output table

# 컨트롤러 Reconcile 성공 확인
kubectl logs -n kube-system \
  -l app.kubernetes.io/name=aws-load-balancer-controller \
  -f --tail=50
```

## 6. 회고 (Retrospective)

### 6.1 잘된 점 (What went well)

- aws-load-balancer-controller 로그를 직접 확인하여 에러 메시지로부터 원인을 신속하게 식별함
- 근본 원인(SG 태그 미설정)을 빠르게 파악하고 단순한 태그 추가 한 번으로 복구 완료 — 코드 변경이나 재배포 없이 해결됨
- 컨트롤러 Reconcile 메커니즘이 태그 추가 즉시 자동으로 규칙을 복원해주어 수동 개입이 최소화됨

### 6.2 개선이 필요한 점 (What needs improvement)

- aws-lb-controller의 SG 관리 방식(태그 1개 요구)을 사전에 파악하지 못한 채 SG 변경 작업이 수행됨
- NLB Target Unhealthy 및 aws-lb-controller 에러에 대한 알람이 없어 장애 탐지가 서비스 단절 이후로 지연됨
- SG 변경 작업에 대한 공식 체크리스트 및 변경 전 검증 절차가 없었음

### 6.3 교훈 (Lessons Learned)

- **aws-lb-controller는 SG 태그로 관리 대상을 식별한다**: `kubernetes.io/cluster/<name>` 태그가 달린 SG가 정확히 1개여야 하며, 0개이거나 2개 이상이면 Reconcile 실패로 즉시 서비스 장애로 이어진다.
- **SG가 1개일 때는 태그 없이 동작한다**: 이 묵시적 동작이 평소에 문제를 숨겨왔으며, SG 추가로 2개가 되는 순간 잠재된 구성 오류가 표면화된다.
- **NLB 구조 이해가 필수**: NLB는 자체 SG가 없어 트래픽 제어가 노드 SG에 전적으로 의존한다. 따라서 SG 규칙 주입 실패는 즉시 전체 트래픽 단절로 이어지는 고위험 지점이다.
- **신규 SG 추가 = 변경 관리 대상**: SG 자체 변경뿐 아니라 노드그룹에 SG를 추가/제거하는 행위도 aws-lb-controller 동작에 영향을 미치므로 반드시 변경 관리 절차를 따라야 한다.
