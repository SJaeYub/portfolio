## 1. 현상 (Symptom)

### 1.1 장애 개요

```
PRD 환경에서 nice-watch-change-file-load-job-workflow 수행 시,
workflow 자체는 completed 상태로 정상 종료되고 서비스 처리도 정상이었으나,
jflow(사내 배치 관리 시스템)에서 해당 배치 작업이 Error로 보고됨.
동일 조건의 STG 환경에서는 정상 동작하여 환경 간 차이가 존재함.
```

### 1.2 현상 상세

- **영향받은 서비스/시스템**: BIZ 도메인 — `nice-watch-change-file-load-job-workflow` (Argo Workflow), jflow
- **오류 메시지 / 증상**:
  ```
  business-app-sa cannot patch resource "pods" in API group ""
  in the namespace "convenience" — 403 Forbidden
  ```
- **정상 동작 기준**: Workflow 완료 후 jflow에 성공(Success) 상태로 보고
- **비정상 동작 내용**: Workflow 및 서비스 처리는 정상 완료되었으나, Argo Workflow 엔진이 pod 상태 업데이트(patch) 시 Forbidden 에러가 발생하여 jflow에 Error로 보고됨

### 1.3 영향도

- **서비스 중단 여부**: 부분 중단 (실제 서비스 처리는 정상, 배치 모니터링 오탐)
- **영향 사용자 수**: 운영팀 (jflow 모니터링 담당자)
- **비즈니스 영향**: 배치 모니터링 신뢰도 저하, 실제 서비스 처리에는 영향 없음

## 3. 원인 분석 (Root Cause Analysis) — 5 Whys

### 3.1 직접 원인 (What happened?)

```
Argo Workflow 엔진이 pod 상태를 업데이트하기 위해 PATCH 호출을 시도하였으나,
PRD 환경의 namespace "convenience"에서 business-app-sa ServiceAccount가
pods 리소스에 대한 patch 권한을 보유하지 않아 403 Forbidden 에러로 종료됨.
이로 인해 에러 코드가 jflow로 반환되어 배치 실패로 기록됨.
```

### 3.2 5 Whys 분석

| 단계 | 질문 | 답변 | 근거/증거 |
|------|------|------|-----------|
| **Why 1** | 왜 jflow에서 배치가 실패로 보고되었는가? | Argo Workflow 엔진이 pod 상태 patch 시 Forbidden 에러를 반환하고 에러 코드로 종료하였기 때문 | k8s 로그: `cannot patch resource "pods"` 403 Forbidden |
| **Why 2** | 왜 pod patch 시 Forbidden 에러가 발생했는가? | PRD 환경의 `business-app-sa`가 namespace `convenience` 내 pods 리소스에 대한 patch 권한을 보유하지 않았기 때문 | k8s RBAC 권한 확인 결과 |
| **Why 3** | 왜 PRD의 `business-app-sa`에 patch 권한이 없었는가? | PRD 환경의 namespace `convenience`에 `argo-workflow-secret-manager` RoleBinding이 설정되어 있지 않았기 때문 | STG/PRD RoleBinding 비교: STG에는 존재, PRD에는 누락 |
| **Why 4** | 왜 PRD에 RoleBinding이 누락되었는가? | STG 환경에 해당 RoleBinding이 추가될 때 PRD 환경에는 동일 설정이 반영되지 않았기 때문 (환경 간 설정 동기화 누락) | GitOps 리포지토리 `sre/system-platform/msa-prod-eks-cluster` 이력 확인 |
| **Why 5** | 왜 환경 간 설정 동기화가 누락되었는가? | STG에 RBAC 설정 변경 시 PRD 동시 적용 여부를 검증하는 프로세스 또는 자동화 체계가 없었기 때문 | 변경 이력 및 배포 프로세스 확인 |

### 3.3 근본 원인 (Root Cause)

```
STG 환경에 Argo Workflow RBAC 설정(RoleBinding) 변경 시,
PRD 환경에 동일 설정을 적용하는 프로세스가 부재하여
환경 간 권한 설정이 불일치한 상태로 운영됨.
```

### 3.4 기여 요인 (Contributing Factors)

- Argo Workflow 엔진의 pod patch 실패가 서비스 처리 결과와 무관하게 배치 전체 에러로 기록되는 동작 방식
- STG와 PRD 환경의 RBAC 설정을 일괄 비교·검증하는 자동화 수단 부재

```
argo-workflow 영역(workflow Role/RoleBinding 관리)에 PRD 환경 추가:

  - name: argo-workflow-secret-manager
    role: argo-workflow-secret-manager
    kind: group
    subjects: system:serviceaccounts:convenience
    verbs: [patch] on resource: pods

STG 환경의 RoleBinding과 동일하게 PRD에 적용 완료.
```

## 6. 회고 (Retrospective)

### 6.1 잘된 점 (What went well)

- 실제 서비스 처리에는 영향이 없어 사용자 피해 없이 처리됨
- k8s 로그를 통해 Forbidden 에러 원인을 빠르게 특정할 수 있었음
- GitOps 기반 인프라 관리로 변경 이력 추적이 용이했음

### 6.2 개선이 필요한 점 (What needs improvement)

- STG 변경 사항이 PRD에 자동으로 반영되지 않는 구조적 문제
- 환경 간 RBAC 설정 불일치를 사전에 감지하는 자동화 수단 부재
- jflow 에러 보고 시 실제 서비스 처리 성공 여부를 함께 제공하지 않아 혼선 발생

### 6.3 교훈 (Lessons Learned)

- STG/PRD 환경 간 설정 일관성은 수동 프로세스에만 의존하지 않고 자동화로 보장해야 함
- 배치 모니터링 시스템(jflow)의 에러가 실제 서비스 장애를 의미하지 않을 수 있으므로, 에러 분류 체계 정교화 필요
