## 3. 원인 분석 (Root Cause Analysis) — 5 Whys

### 3.1 직접 원인 (What happened?)

```
EKS 환경에서 etf-service 컨테이너 이미지 빌드 시,
Gradle이 의존성 다운로드를 위해 build.gradle의 repositories 블록 선언 순서에 따라
사내 Nexus가 아닌 외부 저장소(repo.maven.apache.org)를 1순위로 먼저 호출하였음.

EKS 클러스터는 보안 정책상 외부 인터넷 통신이 패킷 Drop 방식으로 차단되어 있어
TCP 연결이 즉시 거부(RST)되지 않고 connectTimeout(30~60초) 만료까지 무응답 대기가 발생함.
의존성 수백 개에 대해 이 timeout 대기가 반복되면서 GitLab CI의 1시간 제한에 도달,
빌드가 강제 종료됨.
```

### 3.3 근본 원인 (Root Cause)

```
build.gradle의 repositories 블록에 외부 Maven 저장소(mavenCentral())가
사내 Nexus보다 먼저 선언되어 있어, EKS 폐쇄망 환경에서 Gradle이
매 의존성마다 외부 저장소 connectTimeout을 대기하게 됨.
수백 개 의존성 × 30~60초 timeout = 총 빌드 시간 1시간 초과로 파이프라인 강제 종료.
```

### 3.4 EKS 패킷 Drop 방식의 기술적 원리

EKS 환경에서 외부 통신을 차단하는 레이어는 총 3곳이며, 모두 기본적으로 **패킷 Drop(무응답)** 방식으로 동작한다.

#### (1) AWS Security Group
EC2/EKS 노드에 부착하는 화이트리스트 기반 방화벽. 명시적으로 허용되지 않은 트래픽은 자동으로 Drop(무응답) 처리된다. Reject(RST 반환)와 달리 응답 패킷을 전혀 보내지 않는다.

```
# EKS 노드 Security Group 아웃바운드 예시
허용: 10.0.0.0/8 (사내망)
묵시적 Drop: 그 외 모든 트래픽 (repo.maven.apache.org 포함)
```

#### (2) Kubernetes NetworkPolicy (Pod 레벨)
클러스터 내 Pod의 egress(외부 송신) 트래픽을 제어. NetworkPolicy가 하나라도 적용되면 명시되지 않은 모든 트래픽이 Drop된다.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - ipBlock:
        cidr: 10.0.0.0/8  # 사내망만 허용
    # 외부 IP → 명시 없음 → 자동 Drop
```

#### (3) AWS NACL (Network ACL)
VPC 서브넷 레벨에서 적용. Security Group과 달리 명시적 DENY 규칙을 넣을 수 있으나, 기본 구성에서는 허용 외 트래픽을 Drop 처리한다.

#### Drop vs Reject: Gradle fallback에 미치는 차이

```
[Drop 방식 — EKS 실제 환경]
Gradle → TCP SYN → repo.maven.apache.org
                          ↓
                    (패킷 버려짐, 응답 없음)
                          ↓
         Gradle HttpClient: "응답이 없는데... 느린 건가?"
         → connectTimeout(30~60초) 만료까지 대기
                          ↓
         timeout 후 에러 → 그제서야 Nexus로 재시도
         → 의존성 1개당 30~60초 낭비

[Reject 방식 — RST 즉시 반환]
Gradle → TCP SYN → 방화벽
                      ↓
               RST 패킷 즉시 반환
                      ↓
         Gradle: "연결 거부됨 → 즉시 Nexus로 fallback"
         → 의존성 1개당 수십 ms 이내 처리
```

Gradle은 내부적으로 `HttpClient`의 `connectTimeout` 만료 전까지 재시도 없이 대기한다.
Drop 환경에서는 이 대기가 **의존성 수만큼 반복**되어 시간이 선형으로 증가한다.

```
총 낭비 시간 = 의존성 수(수백 개) × connectTimeout(30~60초)
             ≒ 수천 초 >> GitLab CI 1시간 타임아웃 초과
```

Nexus request.log에서 `08:50~09:24`(약 34분)간 30초 이상 응답 지연 요청이 대량 확인된 것이
바로 이 현상의 직접적인 증거다.

### 3.5 기여 요인 (Contributing Factors)

- EKS 네트워크 정책이 외부 트래픽을 패킷 Drop 방식으로 차단하여 Gradle의 즉각적인 fallback을 막음
  - Connection Refused(RST) 방식이었다면 즉시 실패 후 Nexus로 넘어가 영향 최소화 가능
- `allprojects { repositories {} }` 와 최상위 `repositories {}` 블록이 병존하면서 우선순위 혼선 발생
- 동일 Nexus를 사용하는 타 프로젝트(B)와의 설정 표준화가 이루어지지 않은 상태로 운영됨
- Gradle Daemon이 캐시 없이 최초 기동되어 모든 의존성을 원격에서 다운로드 필요 (로컬 캐시 없음)

```groovy
// 수정 전 (문제)
repositories {
    mavenCentral()  // 외부 저장소 1순위 → EKS 폐쇄망에서 connectTimeout 발생

allprojects {
    repositories {
        maven { url "https://사내-nexus/repository/maven-release-group/" }
    }

allprojects {
    repositories {
        maven { url "https://사내-nexus/repository/maven-release-group/" }  // Nexus 1순위
        // mavenCentral() 제거 — Nexus가 Maven Central proxy 역할을 하므로 불필요
    }

```

**[조치 2] (권고) settings.gradle에 저장소 일괄 강제 선언 추가**

```groovy
// settings.gradle
dependencyResolutionManagement {

    // mavenCentral() 등이 build.gradle에 잔존해도 완전히 무시되어 재발 방지 가능
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories {
        maven { url "https://사내-nexus/repository/maven-release-group/" }
    }
}
```

### 5.3 장애 대응 프로세스 개선

```
- 폐쇄망(EKS) 환경에서의 Gradle 프로젝트는 외부 저장소를 repositories에 선언하지 않는 것을
  코드 리뷰 체크리스트 항목으로 추가.

- Nexus를 사내 Maven proxy로 활용하는 경우, mavenCentral() 등 외부 저장소 직접 선언은
  불필요하며 보안 및 빌드 안정성 측면에서도 제거가 원칙임을 팀 내 공유.

- 빌드 타임아웃 발생 시 1차 점검 항목으로 "외부 저장소 접근 시도 여부"를 런북(Runbook)에 추가.

- STG/PRD 동일 인프라 환경에서 프로젝트 간 build.gradle 설정 표준화 기준 수립.
```

## 6. 회고 (Retrospective)

### 6.1 잘된 점 (What went well)

- Nexus `request.log` 분석(`awk '$NF > 30000'`)을 통해 병목 지점을 빠르게 저장소 레벨까지 좁혔음
- 동일 Nexus를 사용하는 B 프로젝트와의 비교 분석으로 서버 자체 문제를 조기에 배제하여 불필요한 인프라 조치를 막았음
- GitLab 파이프라인 로그 → Nexus 로그 → build.gradle 코드 순으로 레이어를 좁혀가는 체계적인 접근으로 근본 원인을 정확히 식별함

### 6.2 개선이 필요한 점 (What needs improvement)

- EKS 폐쇄망 환경에서 외부 저장소를 참조하면 패킷 Drop으로 인해 timeout이 발생한다는 사실이 팀 내 공유되지 않아 설정 오류가 장기간 잠재됨
- Gradle `repositories {}` 블록 선언 순서가 빌드 성패에 미치는 영향에 대한 팀 내 인식 부재
- 프로젝트 간 `build.gradle` 설정 표준화 기준이 없어 동일 인프라에서 상이한 설정으로 운영됨
- 빌드 타임아웃 발생 시 네트워크 레벨 원인(외부 저장소 접근)을 우선 점검하는 런북 부재

### 6.3 교훈 (Lessons Learned)

- **Gradle repositories 선언 순서는 빌드 환경에 따라 치명적인 영향을 미칠 수 있음**
  외부 통신이 가능한 환경에서는 문제 없이 동작하던 설정이, 폐쇄망(EKS)에서는 수백 건의 timeout 누적으로 이어져 빌드 전체를 실패시킴

- **방화벽의 차단 방식(Drop vs RST)이 장애 패턴을 결정함**
  패킷 Drop 환경에서는 Gradle이 즉시 fallback하지 못하고 connectTimeout까지 대기하므로, 아주 작은 설정 오류가 수십 분의 지연으로 증폭됨. RST 방식이었다면 수 ms 이내 fallback하여 영향이 없었을 것

- **Nexus request.log는 의존성 다운로드 병목 진단의 핵심 증거**
  응답시간 필터링(`awk '$NF > 30000'`)으로 수 분 내 병목 지점 특정 가능. 유사 장애 발생 시 1차 점검 대상으로 활용할 것
