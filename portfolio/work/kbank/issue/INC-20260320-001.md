## 1. 현상 (Symptom)

### 1.1 장애 개요

```
타 업무 담당자로부터 대내계/대외계 통신의 MSA 응답 지연 발생 공유를 받음.
Grafana 확인 결과 특정 서비스들의 Pod 가용성이 100% → 75%로 저하된 것을 확인.
k9s 콘솔에서 해당 파드들이 기동 중인 EKS 워커 노드 1대가 NotReady 상태인 것을 확인.
AWS 측 문의 결과 underlying hardware 이슈로 해당 노드의 네트워크가 유실된 것으로 확인됨.
```

### 1.2 현상 상세

- **영향받은 서비스/시스템**: 대내계/대외계 연동 MSA 서비스 (특정 EKS 워커 노드에 기동 중이던 파드 전체)
- **오류 메시지 / 증상**:
  ```
  # k9s / kubectl describe node <NODE_NAME> — Conditions 섹션
  Type              Status    Reason
  ----------------  --------  --------
  Ready             Unknown   NodeStatusUnknown
  MemoryPressure    Unknown   NodeStatusUnknown
  DiskPressure      Unknown   NodeStatusUnknown
  PIDPressure       Unknown   NodeStatusUnknown
  NetworkUnavailable Unknown  NodeStatusUnknown

  → 모든 Condition이 Unknown 상태: kubelet이 API 서버로의 하트비트를 완전히 중단한 상태
  → kubelet은 기본 10초 주기로 Lease 갱신, 40초 이상 신호 없으면 노드 컨트롤러가 전 Condition을 Unknown으로 전환
  → 네트워크 단절로 인해 노드-컨트롤플레인 간 통신 불가 확인
  ```
- **정상 동작 기준**: 워커 노드 Ready 상태 유지, Pod 가용성 100%
- **비정상 동작 내용**: 워커 노드 1대 NotReady (전 Condition Unknown), 해당 노드 기동 파드 서비스 불가, Pod 가용성 75%로 저하

### 1.3 영향도

- **서비스 중단 여부**: 부분 중단 (노드 1대 NotReady, 잔여 노드 파드는 정상)
- **영향 사용자 수**: 대내계/대외계 연동 MSA를 사용하는 서비스 이용자
- **비즈니스 영향**: 대내계/대외계 MSA 응답 지연 발생. Pod 가용성 75% 수준으로 저하됨에 따른 처리 능력 감소

## 3. 원인 분석 (Root Cause Analysis) — 5 Whys

### 3.1 직접 원인 (What happened?)

```
AWS EKS 워커 노드 1대에서 underlying hardware 이슈로 인해 해당 EC2 인스턴스의
네트워크 연결이 완전히 유실됨.
네트워크 단절로 kubelet이 API 서버와의 통신(하트비트 Lease 갱신)이 불가능해지고,
Kubernetes 노드 컨트롤러가 40초 이상 하트비트 미수신을 감지하여
해당 노드의 모든 Condition을 Unknown으로 전환하여 NotReady 상태로 변경.
이로 인해 해당 노드 위의 파드들이 서비스 불가 상태가 되어 MSA 응답 지연이 발생함.
```

### 3.2 5 Whys 분석

| 단계 | 질문 | 답변 | 근거/증거 |
|------|------|------|-----------|
| **Why 1** | 왜 대내계/대외계 MSA 응답 지연이 발생했는가? | 특정 EKS 워커 노드가 NotReady 상태가 되어 해당 노드 위의 파드들이 서비스 불가 상태가 됐기 때문 | Grafana Pod 가용성 100% → 75% 저하 확인 |
| **Why 2** | 왜 워커 노드가 NotReady 상태가 됐는가? | kubelet이 API 서버로의 하트비트(Lease 갱신)를 중단하여 노드 컨트롤러가 모든 Condition을 Unknown으로 전환했기 때문 | kubectl describe node: 전 Condition Unknown 확인 |
| **Why 3** | 왜 kubelet의 하트비트가 중단됐는가? | 해당 노드의 네트워크 연결이 완전히 유실되어 API 서버와의 통신이 불가능해졌기 때문 | Conditions의 NetworkUnavailable Unknown 상태 확인 |
| **Why 4** | 왜 노드의 네트워크 연결이 유실됐는가? | AWS underlying hardware 이슈로 해당 EC2 인스턴스 수준에서 네트워크가 끊겼기 때문 | AWS 측 문의 공식 답변: "underlying hardware issue" |
| **Why 5** | 왜 AWS 하드웨어 이슈가 발생했는가? | AWS 인프라 물리 장비 장애로, 애플리케이션/설정 수준에서 제어 불가능한 외부 요인 | AWS 측 답변 (인프라 영역, 내부 통제 불가) |

### 3.3 근본 원인 (Root Cause)

```
AWS EC2 기반 EKS 워커 노드의 underlying hardware(물리 인프라) 장애로 인해
해당 인스턴스의 네트워크 연결이 유실됨.
이는 AWS 인프라 영역의 문제로 애플리케이션 또는 설정 수준에서의 예방은 불가능하며,
빠른 탐지 및 노드 교체로 영향을 최소화하는 것이 핵심 대응 방안임.
```

### 3.4 기여 요인 (Contributing Factors)

- 노드 NotReady 발생 시 즉각 알람 체계 부재 → 타 업무 담당자 공유를 통해 뒤늦게 인지
- EKS 노드 수가 적을 경우 1대 장애 시 Pod 가용성 저하 폭이 큼 (노드 4대 기준 1대 장애 = 25% 감소)
- Kubernetes의 노드 장애 감지 → 파드 재스케줄링까지 일정 시간(기본 5분) 소요되는 구조적 지연

### 4.2 임시 조치 (Workaround)

```
영향받은 파드들에 대해 kubectl rollout restart 명령으로 정상 노드로의 강제 재기동 시도.
단, 일정 시간 경과 후 Kubernetes가 NotReady 노드의 파드들을 정상 노드로 자동 재스케줄링하면서
서비스가 자연 정상화되어 수동 rollout은 실제 적용되지 않음.
```

```bash
# 시도한 rollout restart 명령 (자연 정상화로 대체됨)
kubectl rollout restart deployment/<DEPLOYMENT_NAME> -n <NAMESPACE>
```

### 4.3 근본 조치 (Permanent Fix)

```
1. 자연 정상화 확인 (NotReady 노드의 파드 → 정상 노드로 자동 재스케줄링 완료)

2. 문제 노드 교체
   - 기존 노드 그룹에서 NotReady 노드를 제거
   - 신규 노드를 노드 그룹에 추가하여 클러스터 정상 구성 복구
```

```bash
# 노드 교체 절차
# 1. 신규 파드 스케줄링 차단
kubectl cordon <NODE_NAME>

# 2. 기존 파드 안전하게 드레인 (DaemonSet 제외, emptyDir 데이터 삭제 허용)
kubectl drain <NODE_NAME> --ignore-daemonsets --delete-emptydir-data --force

# 3. 노드 그룹에서 해당 인스턴스 제거 (관리형 노드 그룹이면 ASG가 신규 노드 자동 프로비저닝)
aws ec2 terminate-instances --instance-ids <INSTANCE_ID>
```

## 6. 회고 (Retrospective)

### 6.1 잘된 점 (What went well)

- Grafana를 통해 Pod 가용성 저하를 수치로 빠르게 확인할 수 있었음
- k9s와 kubectl describe node를 통해 Conditions 상태를 정확하게 분석하여 네트워크 단절 원인을 빠르게 좁혔음
- Kubernetes의 자체 복구 메커니즘(NotReady 노드 파드 자동 재스케줄링)이 정상 동작하여 서비스가 자연 정상화됨
- AWS 측 문의를 통해 근본 원인(underlying hardware)을 공식 확인하고 문서화함

### 6.2 개선이 필요한 점 (What needs improvement)

- 노드 NotReady 발생 시 모니터링 알람이 없어 타 팀의 장애 공유로 뒤늦게 인지
- Kubernetes 파드 자동 재스케줄링 기본 대기 시간(5분)이 길어 그 사이 응답 지연 발생
- AWS 하드웨어 이슈와 같이 외부 요인에 의한 노드 장애 시 즉각 대응 기준(런북)이 부재

### 6.3 교훈 (Lessons Learned)

- EKS 노드의 Conditions 전체 Unknown은 네트워크 단절 또는 kubelet 완전 중단을 의미하며, 이 경우 노드 수준의 로그보다 AWS EC2 Status Check 및 AWS 측 문의가 더 빠른 원인 파악 경로임
- Kubernetes는 하드웨어 장애에 의한 노드 NotReady 상황에서 일정 시간 후 파드를 자동 재스케줄링하는 복원력을 가지고 있으나, tolerationSeconds 값에 따라 복구 시간이 달라지므로 운영 정책에 맞게 조정이 필요함
- 외부 인프라(AWS) 의존성이 있는 시스템에서는 AWS Health Dashboard 이벤트 알람 연동이 선제 대응에 유효함
